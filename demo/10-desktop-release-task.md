# AVE 三桌面平台 Demo Release 任务书

**交付目标**　在团队仓库 `player-Muteki/ave` 发布一个可下载的桌面 Demo Release。同一源码版本交付 macOS、Windows 和 Linux 安装包。用户安装后能导入本地视频，用自然语言提出剪辑要求，审阅方案，播放预览，批准导出，再打开成品视频。

**立项基线**　以已合并 PR #10 的 `aac3650` 为起点。既有 Linux 开发包记录和 Chrome 回归可作对照。三端最终包须各自留下本版本的验收证据。建议版本号为 `v0.1.0`，正式打标签前核对是否已被使用。

**平台范围**　本版按 macOS Apple Silicon、Windows x64 和 Linux x64 验收。已构建的 Intel Mac DMG 作为附加下载；其测试结果不参与本版发布判断。项目的长期目标见[产品交付标准](01-product.md)。Windows 首发以 Windows 11 为验收环境，Linux 以 Ubuntu 24.04 为验收环境。发布页只列实际通过的系统和架构。本轮功能验收聚焦确定性剪辑；Android 和长镜头生成列入后续版本。

## 一、修复与回归

每项先在基线上保存失败断言，再修实现，在同一输入上验证修复。共享接口有改动时，先更新 v1 兼容契约、JSON Schema 和正反样例，再更新服务端及调用端。修复和回归测试一起提交。

| 步骤 | 实施内容 | 验收要求 |
| --- | --- | --- |
| 1　静音剪切 | 统一波形的 RMS 单位、静音阈值和最短时长。只在用户选区内寻找连续静音。没有符合条件的区间时提示原因。对触及素材开头、结尾的剪切生成合法方案。 | 全段有声且 RMS 为 0.8，在选区 0.550–1.500 秒不提交方案。混合有声与静音样片只删除选区内合格的静音段。覆盖非整桶边界、静音太短、开头和结尾。真实导出后检查音频及剩余片段。 |
| 2　历史方案与分页 | 按项目和方案 ID 从持久化记录读取旧方案。列表使用稳定排序和与其一致的游标，定义最后一页行为。 | 建立 130 个方案，覆盖相同 revision 与非顺序 ID。逐页取回 130 个不同 ID，无缺失、无重复；最早的方案可按 ID 查看。换项目访问被拒绝。重启后结果一致。 |
| 3　运行事件 | 服务端按项目、run 和序号查询。工作台保存已消费的位置；切换项目或运行时使用对应游标。 | 单次运行产生 205 个事件，两页取回 200 和 5 个，序号连续对应原记录；再刷为空。穿插超过 2,000 条其他运行的事件，目标事件仍可取回。覆盖切换运行和断线后继续读取。 |
| 4　上传中取消 | 上传过程保留可用的取消按钮。停止后续分块、处理已在途请求，并让客户端及服务端对“取消或提交谁先完成”返回相同终态。 | 在真实工作台传输多分块文件，第一块被服务端确认后点击取消。取消成功时停止发送，项目没有新资产，服务端释放临时分块。连续点取消、取消后重传均正常。若提交已先成功，界面显示实际结果。 |
| 5　AI 按方案 ID 预估 | 让 AI 工具的 schema、描述、broker 和桌面 RPC 支持相同的方案 ID 调用；保留已有草稿调用。由 daemon 绑定项目范围。 | 旧草稿调用继续通过。仅给已保存的 planId 即可返回方案 ID、时长与校验结果；未知或跨项目 ID 返回可识别错误。通过实际规划 Worker 调用一次，并保存脱敏工具记录。 |
| 6　分数采样率 | 用精确有理数校验并保存采样率，统一处理非法输入和约定的 1–1000 fps 边界。检查任务、媒体分析命令和报告使用同一时基。 | 25/1、24000/1001、30000/1001 保持等值；零分母和非法值被拒绝，边界行为有契约测试。以分数帧率样片检查切点与源帧 PTS，对齐误差不得随时长累积。 |

## 二、集成、构建与交付

| 步骤 | 实施内容 | 验收与证据 |
| --- | --- | --- |
| 7　冻结候选源码 | 从干净 checkout 恢复锁定 Paseo 上游，叠加本仓库 `downstream/paseo`，按 lockfile 安装和运行 postinstall。记录 AVE、上游、Node、Electron、FFmpeg 版本。 | 六项专项回归、服务端行为测试、TS/Worker 契约对照、真实 Chrome 工作台和项目校验通过。记录候选 SHA、测试报告和运行环境。后续若改代码，从新 SHA 重建受影响包并重验。 |
| 8　接通三端构建 | 在团队仓库接入原生 macOS、Windows、Linux 构建任务。配置 AVE 应用身份，更新源指向团队仓库或在首版关闭。确定 FFmpeg、ffprobe、Worker 及其运行库的随包交付方式，记录许可。检查 Actions、测试设备和规划模型的可用性。 | 新 runner 按锁恢复依赖；包内可定位并启动 daemon、规划 Worker、FFmpeg 与 ffprobe。开发机的绝对路径、API 密钥与模型凭据不进入包。每个产物可追溯至同一候选 SHA。 |
| 9　安装包校验与原生安装 | 为各目标生成下表的最终文件，记录每份安装包的 SHA-256，在发布页说明本版采用未签名分发；在干净用户环境中安装，直接从用户入口启动。 | 最终安装文件逐项通过下表，留存安装和启动日志。若平台设备或 runner 缺失，报告具体阻塞及受影响产物，其余平台继续验证。 |
| 10　端到端演示 | 在每个平台安装的应用中创建项目，导入同一份有原声、非零起始时间戳的 2.4 秒 MKV。输入“保留最后一秒和原声”，先拒绝一次，再生成并批准，播放预览、批准成品、导出 MP4。 | 实际配置的模型生成播放区间 [1.4, 2.4)；批准前仅允许素材分析，拒绝的方案不渲染。输出完整解码、有原声，音视频时长和时间戳符合一秒样片及编码时间基容差。核对源 SHA-256 未变、成品 SHA-256 与清单一致。记录模型标识、审批、ffprobe、解码日志和窗口截图。 |
| 11　发布和下载复验 | 在团队仓库建立草稿 Release，上传各端安装包、SHA256SUMS、版本说明、安装/模型配置说明、许可证及 SBOM。标明已测系统、架构、模型与已知限制。 | 从草稿下载实际附件，逐个核对哈希与已验收文件一致。全部通过后发布；用普通用户入口再次下载验证。交付物为 Release 链接、源码 tag/SHA、各平台附件和对应验收报告。 |

## 三、责任与发布判断

沿用[团队分工](07-team-workflow.md)，建议 K 负责契约、集成与发版，L 负责媒体时基、导出 QA 和上传服务端，C 负责桌面交互、安装包和三端启动，J 参与事件分页、权限与重连复验。具体执行时可调整人选，以交付证据归档。

最终报告按“缺陷编号或平台｜源码 SHA｜产物 SHA-256｜运行环境｜验证结果｜日志或截图”登记。每项使用待执行、通过、失败或阻塞，并记录失败输入及修复后复测。只有六项修复和全部目标平台的最终包验收通过、GitHub Release 附件可下载，才将本任务标记为完成。若已公开版本发现阻断缺陷，按[发布与回滚约定](08-delivery.md)发布更高版本的修正版。
